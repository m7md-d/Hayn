## قرارات المستخدم والتعليمات التي لا تضيع

- **DarkLib باقية**. المطلوب إصلاحها وتحديد حدودها، لا إلغاؤها أو الرجوع الكامل إلى main. المقارنة السابقة أوضحت أن main نفسه يحتوي أخطاء وأن الرجوع لا يعالجها كلها.
- **المنطق الثقيل في DarkLib (قرار المستخدم 2026-10-02):** المعقد والثقيل من منطق التحويل يكون في DarkLib، لأن هدفها أن يصير التحويل مهمة موثوقة لا يحتاج من يستدعيها إلى التفكير فيها. الاستثناء: ما يكون أداؤه أفضل خارجها، بقياس. الجسور الأصلية تبقى لما لا يصل إليه غير النظام (فك HEVC، ImageIO، MediaCodec)، وDart يرتب الخطوات ويسجل التشخيص.
- الهدف مكتبة صغيرة تمنح واجهة موحدة وسياسة وسيطة خاصة بنا، مع codecs وخدمات منصة ناضجة. لا تتحول إلى إطار صور/فيديو/صوت ضخم، ولا تُنشر كمكتبة مستقلة ضمن العمل الحالي.
- معالجة الميديا محلية وأوفلاين، بلا رفع صور أو تتبع. تنزيل اعتماديات التطوير لا يغير هذا الوعد. PhotoKit/MediaStore والصلاحيات والواجهة تبقى مسؤوليات التطبيق والمنصة.
- الاستبدال الذكي/الجراحي أزيل عمدًا بسبب قيود المنصات والمشاكل السابقة؛ لا تعِد تنفيذه أو تفتح نقاش إحيائه ضمن دفعة التصحيح.
- نوسع التحويل بين الصيغ مع حفظ صحيح لما تستطيع الوجهة تمثيله. الجودة lossy المختارة لا تعني إذنًا بإسقاط اللون أو الشفافية أو الأبعاد. عند التعارض يلزم رفض واضح أو سياسة فقد صريحة، لا وعد مستحيل.
- **سياسة HDR (قرار المستخدم 2026-09-28):** لا منع ولا تحذير. HDR يُحفظ حيث يثبت مساره، وإلا يتحول بصمت إلى نسخة SDR صحيحة، مع تشخيص داخلي. التحذير يزعج المستخدم العادي، والمحترف ينزعج من شرح عمله. نسخة SDR الصحيحة هي أساس gain map بعد التحقق أنه SDR، أو tone mapping من النظام لـPQ/HLG؛ الرفض فقط لما لا يمكن إنتاجه صحيحًا.

## الخطوة الأولى بالتفصيل: IMG-05

هذا تصميم مقترح، وليس API موجودة. مواضع البداية: [ImageEncoder](../lib/features/image_ops/data/image_encoder.dart)، [ImageProbe](../lib/features/image_ops/data/image_probe.dart)، [NativeImageProbe](../lib/features/image_ops/data/native_image_info.dart)، [DarkLibCore](../lib/core/darklib/darklib.dart)، وجسرا [iOS](../ios/Runner/AppDelegate.swift) و[Android AVIF](../android/app/src/main/kotlin/app/naqaa/hayn/AvifHwEncoder.kt).

1. اجمع حقائق **المصدر الأصلي قبل أي bake أو تصغير**: الصيغة والأبعاد المخزنة/المعروضة والعمق واللون/dynamic range والاتجاه والشفافية والعناصر المساعدة، مع مصدر الدليل والحالة unknown عند غياب فحص موثوق. لا تستنتج SDR من غياب nclx ولا HDR من 10-bit/P3 وحدهما. اجعل الفحص محدود الموارد.
2. افصل الطلب إلى متطلبات حفظ وفقد مسموح وسياسة خصوصية. `keepMetadata=false` لا يعني حذف ICC؛ `allowFormatFallback=true` لا يعني السماح بـflatten أو تغيير الأبعاد. HDR يتبع سياسة المستخدم: يُحفظ حيث يثبت المسار، وإلا نسخة SDR صحيحة بصمت. حافظ على default الصيغة المحددة وعلى سلوك Auto المصرح به.
3. خطط للـbackend حسب **العملية والخصائص**، لا اسم الصيغة فقط. امنع مبكرًا المسار RGBA8/Bitmap/I420 عندما يتعارض مع حفظ مطلوب. اجعل جسر HEIC→PNG جزءًا من الخطة له قدرات وتحقق، وليس مخرجًا يتجاوز سياسة المصدر الأصلي.
4. عند حفظ إلزامي لا يمكن إثباته، ارفض قبل أول استدعاء ترميز أو حفظ، برمز تشخيص واضح. HDR لم يعد حفظًا إلزاميًا؛ الإلزامي صحة نسخة SDR. لذلك PQ/HLG بلا tone mapping متاح يُرفض قبل أي backend، بما فيه عتاد Android. لا تتنقل بين المحركات بعد رفض متعلق بالحفظ؛ اسمح فقط بتعافٍ يحقق القيود نفسها.
5. بعد التنفيذ أعد فحص الناتج: decode صالح، أبعاد واتجاه وعينات alpha واللون/العمق والعناصر المطلوبة. وجود توقيع صحيح أو قناة alpha أو `tmap` لا يثبت صحة المحتوى. فحص إزالة البيانات الخاصة منفصل؛ فشلها لا يعيد الأصل نجاحًا.
6. اربط تقرير التحقق بالنتيجة وبكل موضع حفظ: الضغط والقص والمهام والمعاينات. لا تستعمل معاينة منخفضة الدقة كملف نهائي. `EncodedImage` الحالي ليس تقرير حفظ كاملًا؛ وسّعه تدريجيًا دون إبقاء منسقَي سياسة دائمين.
7. أبقِ رمز `preservation_required:` الانتقالي حتى يثبت بديل typed على الجسر الحقيقي. FRB يرمي `Result<_, String>` كنص في Dart؛ لا تعد إلى mock من نوع Anyhow. عند تغيير API أعد توليد الروابط بـcodegen **2.12.0** ولا تعدلها يدويًا.

اختبارات القبول الأولى: استدعاء native مسبق كان سيسمح بالنجاح قبل Rust؛ يجب أن يمنعه preflight. gain map بأساس SDR تنجح بصمت وتسجل تشخيص الإسقاط. PQ/HLG تمر بـtone mapping النظام أو تُرفض قبل أي backend. غط HDR مباشر وgain map وunknown، alpha true/false/null، privacy، هدف محدد وAuto، تعافي داخل الصيغة ورفض نهائي؛ أثبت أن backend وGallerySaver لا يُستدعيان بعد رفض حفظ. ثم نجاح SDR عادي ومسارات أساسية حقيقية حتى لا يصبح الإصلاح رفضًا شاملًا لكل الصور.

## خطة corpus والقياس التي لم تنفذ كاملة

المودع الآن عينتان عامتان من libavif مع الرخصة والـhash في [fixtures/README](../native/darklib/tests/fixtures/README.md): PQ وISO gain map. لا تضف مكتبة صور كبيرة إلى Git أو assets الإنتاج. العينات الأقدم في نسخة الفحص أدناه تحتاج مراجعة مصدرها ورخصتها وبصمتها قبل ترحيلها.

المطلوب تدريجيًا: JPEG/PNG/WebP SDR؛ alpha بقيم متفاوتة وشبكات مع alpha؛ Display P3/ICC وCICP دون ICC؛ اتجاهات 1–8 وirot/imir وcrop؛ PQ وHLG؛ Apple gain map القديم وISO/Adaptive HDR كلٌ منفصل؛ JPEG Ultra HDR/MPF؛ gain map بقاعدة SDR وأخرى HDR؛ صور كبيرة ومعطوبة. استخدم أصغر عينات كافية، وصور iPhone مأذونًا بها عند توفرها، ولا تستنتج خصائصها من اسم الهاتف.

لكل حالة سجّل: المصدر والرخصة وSHA-256، النظام والمحرك والإصدار، graph والعناصر والتحويلات والأبعاد واللون والعمق قبل وبعد، إعدادات الجودة الفعلية، طريقة التحقق، والنتيجة أو سبب الرفض. افصل صحة البنية، البكسلات، العرض الملوّن، HDR، الخصوصية، ثم قبول الملف واسترجاعه من المعرض.

اقرأ مراجع [بحث HDR](11-HDR-RESEARCH.md) الأصلية مجددًا قبل تغيير تفسير البروتوكول: Apple WWDC23/24 وImageIO، AVIF/HEIF، Android Ultra HDR وEncoderCapabilities. البحث السابق ليس بديلًا عن مراجعة الجزء الذي ستعدله. لا تعِد تسمية grid بأنها شبكة HDR ولا تعتبر عدد الصور الظاهر في ImageIO جردًا لكل عناصر الحاوية.

مقارنة AVIF المؤجلة: نفس المصدر والعملية والأبعاد والعمق والألفا واللون، جودة بصرية متقاربة، backend/codec/rate control/subsampling، زمن وpeak memory وحجم الناتج على أجهزة بقدرات مختلفة. قياس حجم المكتبة نفسها قبل/بعد لكل ABI وزمن البناء. libavif مرشح تجربة معزولة بأقل codecs، وليس اعتمادًا مصرحًا بإضافته تلقائيًا. assembly المعطل وخيوط فك AVIF الحالية فرص قياس، لا دليل اختناق مثبت.
